# Правила работы с репозиторием

## Система версий — обязательна

Любое изменение кода идёт через git. Прямых правок «в рабочей копии без следа» не
должно быть: если что-то поменялось, это отдельный коммит с внятным сообщением.

1. Ветки:
   - `main` — всегда рабочее состояние: `make test` и `make lint` зелёные.
   - `fix/<тема>` — исправление дефекта.
   - `feat/<тема>` — новая возможность.
   - `research/<тема>` — эксперименты со стратегиями и параметрами; вливается в
     `main` только вместе с отчётом об измерении.
   - `chore/<тема>` — инфраструктура, документация, зависимости.
2. Коммиты — Conventional Commits, английский тип, русское описание:
   `fix(paper): ограничить историю терминальных ордеров`.
   Один коммит — одна причина изменения. Не смешивать форматирование и логику.
3. Ветка вливается в `main` через `git merge --no-ff`, после прогона `make test`
   и `make lint` на этой ветке.
4. Релизы помечаются аннотированными тегами semver: `v0.2.0`, `v0.2.1`.
   Тег ставится на `main` после обновления `CHANGELOG.md`.
5. `CHANGELOG.md` обновляется в том же коммите, что и изменение: раздел
   `Unreleased`, при выпуске — перенос в версию с датой.
6. В репозиторий не попадают: `.venv/`, `datasets/`, `frontend/node_modules/`,
   `frontend/dist/`, `.env`, логи, sqlite-аккаунты. Это уже в `.gitignore`;
   проверяй `git status` перед коммитом.

## Проверки перед коммитом

```sh
.venv/bin/python -m pytest      # 169+ тестов
.venv/bin/ruff check backend scripts
.venv/bin/mypy backend/app
cd frontend && npm run build    # если менялся frontend
```

## Про прибыльность

Проект исследовательский. Прибыльность не является свойством кода: её нельзя
включить правкой, её можно только измерить и опровергнуть. Любое утверждение о
доходности должно опираться на издержки (комиссии, проскальзывание, adverse
selection) и на данные вне выборки, на которой подбирались параметры. Пока такого
измерения нет, в отчётах пишется «прибыльность не подтверждена».

Живая торговля (`app.mode=live`, `execution.enabled=true`) остаётся выключенной до
отдельной приёмки: см. `docs/LIMITATIONS.md` и `docs/AUDIT.md`.
